V-1 dev tools are compiled only under `REELCUT_DEV_TOOLS`, and the shipping build is the Distribution configuration, which does not set it · V-2 a dev tool is not an op and not a user-visible edit, but it is an ordinary tool (catalog, handler table, gate, parity check) · V-3 screens are captured with `cacheDisplay(in:to:)`, never ScreenCaptureKit or `screencapture`. The tools are specified in spec §7.9's "Dev tools" paragraph and mapped in §7.4.

## Context

Two needs, one instrument: an agent should be able to look at the running app's chrome to debug a layout without a person describing it, and a person should be able to export named screens with a description of each, to draft design requests. The offscreen harness (`tools/proof/harness/`) already `cacheDisplay`s an `EditorViewController` into a PNG with no TCC grant, and it stays the instrument for byte-identical proofs. It can only render what a package on disk plus positional arguments describe: never a sheet, a panel or a state reached by editing. The shape chosen was dev-only MCP tools in the running app (V-1), capturing through the same `cacheDisplay` path (V-3), plus a screen catalog that drives the app into named states. The agent server itself is a product feature and stays in every build; only the dev tools are absent from Distribution. No op, model field, FFI export or schema bump was added. (orig "Phases")

## Decisions

- **A compile-time flag and a Distribution configuration, with the binary checked.** `project.yml` declares Debug, Release and Distribution (a copy of Release) and sets `REELCUT_DEV_TOOLS` for Debug and Release only. `make app` builds Release, so every proof and agent session has the tools, and Xcode's Archive is pinned to Distribution. `make dist` builds Distribution and runs `tools/proof/dist_check.py`, which requires a marker PRESENT in Release's binary (the positive control) and ABSENT from Distribution's. The build mutant, the flag forced on in Distribution, fails `make dist` (D5); hand mutants of the check each fail their named rows. (V-1; orig V0 record)
- **The check greps a 29-byte marker, not a tool name.** Swift string literals of 15 UTF-8 bytes or fewer are stored inline in an `-O` binary's code: `RC_AGENT_PORT` (13) and `unsaved_changes` (15) were found 0 times in Release, `AgentServerEnabled` (18) once, so `snapshot_ui` (11) could never be a needle. `devToolsMarker` is kept live by the startup log line `reelcut-dev-tools-compiled-in, N dev tools`, so a new tool needs no edit to the check. (orig V0 record, "Deviations")
- **One seam, and the frozen server takes wiring only.** `AgentServer+DevTools.swift` holds the dev handler table, off-main set and catalog rows under `#if REELCUT_DEV_TOOLS`, and empty ones under `#else`; Swift takes no `#if` inside a dictionary literal. `AgentServer.swift` merges them (`withDevHandlers`, a union of off-main sets) and the catalog splices the rows BEFORE the file tools, because `recording_probe.py` asserts the last eleven names. The parity check, the gate and the schema checks then cover the dev tools unchanged in both builds; a dev tool reusing a product tool's name keeps the product handler and logs `Reelcut: `. (V-2; orig V0 record)
- **The preview well captures as the canvas background, not black, and not the picture.** `cacheDisplay` does not draw the `AVPlayerLayer` or Metal content. V1's W1 measured the well's mean as [234, 51, 247] with 0 black pixels (the fixture's magenta background), in the live window and in a never-shown window alike. (orig V1 record W1, Q1)
- **`fill_preview` puts `render_frame`'s picture UNDER the canvas overlay for the capture, and takes it out after.** Under keeps 0.9093 of the overlay's core pixels where over keeps 0.0356 (W4 against W5); the 828 it does not keep are translucent overlay pixels (alpha 0.897–0.974) blending with the picture as they do on screen, so V1's 0.99 bar, written for an opaque overlay, is what failed rather than the technique. Left in, the next capture differs by 1 412 918 px (W6), hence the removal. V2a stages an `NSImageView` just above `playerHost`, under `safeGuides` and `overlay`; the fill-above mutant keeps 0 of 3 820 overlay pixels (F2), and an unstage that leaves the fill fails F3 against the run's first capture. (orig V1 record Q1; V2a record)
- **A capture is in the window's colour space.** Its PNG carries the display's profile, where `render_frame`'s carries sRGB. On the built-in screen the filled yellow read [255, 255, 84], so F0's bound is B < 100, not the spec's < 60; the external screen gives 48. (orig V2a record "F0 and colour management")
- **Neither tool depends on the app being active or its window visible.** An agent drives the app while the person works elsewhere. `snapshot_ui`'s covered captures (under an opaque non-activating panel, `v2_cover.swift`) were byte-identical to uncovered ones with the app inactive (V2a's O rows). `perform_menu_item` delivers through its own responder walk of the NAMED project window — first responder down, then window, delegate, controller, document, the app, its delegate, the document controller — and `NSApp.sendAction(_:to:from:)` to the object found, never nil-targeted `performActionForItem`: the nil-targeted mutant M2 handled nothing with the app inactive (D1, D2). (orig Phases V2; V2a record; V2b record, mutant M2)
- **The tools run off main, every AppKit touch an `onMain` hop.** The road map said main thread; `snapshot_ui`'s fill waits on `Exporter.renderFrameReported` and its settle sleeps 20 ms between passes, and the menu tools sleep in their settle. `select_inspector_tab` runs on main. (orig V2a and V2b "Deviations"; V3 record)
- **The layout dump computes `problems`, and lists AppKit's private views apart.** Ambiguous layout, a view whose ALIGNMENT rect (`alignmentRect(forFrame:)`, the rect Auto Layout pins) passes its superview's bounds, and a text field whose intrinsic width exceeds its frame (a wrapping label is exempt). The second rule measured frames until 2026-09-29, and so flagged every label pinned flush by its 2 pt alignment inset — #140 on nine screens, and #129 — which `v2_layout_probe.swift`'s P7 holds it to (a flush label clean, a label whose alignment rect is 10 pt past its container flagged with exactly 10). `hasAmbiguousLayout` answers truthfully in the `-O -wmo` build (L1, L2), but three private `_NSText…` views inside the Text sub-tab's text view answer ambiguous (L3), so a list taking every view would never be empty; problems on `_NS…` views of every kind go to `private_problems`. The truncation rule separates a truncating label from one that fits (L4, L5), exempts wrapping (L6; mutant M5), and found #70 (289.5 > 271). Frames are in capture points with a top-left origin. (orig V1 record Q4; V2a record)
- **L2 expects the filed defects, not an empty list.** The tool's first run over a clean editor found the toolbar's duration label 2 pt past its stack view; the user chose to file it (#129) and have L2 compare `problems` to `KNOWN` by issue number, so a fix makes L2 fail until the entry is removed. A scratch probe found #129 identical at six widths from 900 to 1440 pt on both screens. #129 was the label's alignment inset: with the rule on alignment rects L2 failed `#129 MISSING`, and `KNOWN` is now empty, so L2 expects no problem at all. (orig V2a record; 2026-09-29)
- **A menu item that runs a modal loop is refused, because it wedges the agent.** A `runModal` reached from a menu action services the main queue inside itself (V1's S4: returned after 1.024 s, a queued marker ran INSIDE the call), so the server's `DispatchQueue.main.sync` hop does not deadlock, but the server reads one request at a time and no later request is read until the modal ends. A sheet does not: Export…, Remove Track and Add Media… each returned with their sheet attached in 295–761 ms, no modal window, the main queue not run inside the call (S1). (orig V1 record Q2(b))
- **The refusal is an ALLOW-table mirrored from the spike's inventory.** `UIMenuTable.swift` holds one verdict per selector of `tools/proof/capture_spike/inventory.json` (93); `modal`, `framework` (the sixteen AppKit-owned items: Quit, Open…, Save, Undo, …) and a selector with no row (`unclassified`) are refused by name. The framework refusal matters: with it removed, Undo was performed inside the perform's undo group and the app died ("too many nested undo groups", mutant M1). The inventory's site grep learned the app-modal `presentError(` token (V1's Owed), which made New Project (`AppDelegate.swift:170`, its failure path) `modal`; the `new_project` tool is the capability. A new menu item needs a row in both the inventory and the table, and `v2_menu.py`'s H1/H2 fail until it has them. (orig V1 record Q2(c); V2b record "The inventory decision", mutants M1, M5)
- **Each perform is one undo group and never writes `isEnabled`.** Validation is the target's `validateMenuItem(_:)`, else `validateUserInterfaceItem(_:)`; without the explicit group, two performed edits merged into one undo step (M3), and an always-enabled mutant performed Clear Range with no range and Add Marker under a sheet (M4). (orig V2b record)
- **An answer waits for a settle.** The attached sheet, the app-modal window and the visible window numbers are read every 20 ms until five reads agree, bounded at 3 s, so a sheet that arrives a turn later is in the answer; measured settles were 124–158 ms. The answer's `sheet_at_return` says whether a sheet was attached when the action returned, and `v2_menu.py`'s L1 reaches a late one: Add Marker's edit puts the reverse progress sheet up a run-loop turn after the action, answering `sheet_at_return` false and the sheet after the settle. A settle removed does not fail L1, because the answer's own later main-thread hop already runs after the sheet's `DispatchQueue.main.async`. A menu path names the title the item SHOWS after validation ("Undo Add Marker"). (orig V2b record)
- **`cancel_sheet` closes a sheet through its own Cancel, and file panels are not captured.** A file panel is ended with `.cancel` on its parent, else the sheet's Escape button is pressed, else its only button; anything else is refused naming the buttons. An `NSOpenPanel` sheet's content is an out-of-process `NSRemoteView` and captures as ONE colour (V1's S2c), so `snapshot_ui` refuses a file-panel sheet rather than return a flat picture. `NSSavePanel` was not measured. (orig V1 record Q2(a); V2b record)
- **The look is set at LAUNCH (`-RCDevAppearance light|dark`); the live appearance switch was withdrawn.** V1's A3–A6 found a live `window.appearance` switch and its restore byte-identical to a fresh window, and V2a shipped `appearance` on that basis. That held only against a fresh window built with aqua INSIDE the same dark-system process, which cannot see a colour a view takes once at build time from the launch appearance. Against a Release instance launched light (`-NSRequiresAquaSystemAppearance YES`), V3's review measured the switched light editor different at 389 266 of 1 117 376 px — the inspector 163 654 of 163 856, the preview surround 126 294, the timeline 99 050, the toolbar 268 — and Welcome kept a dark ground where the light launch is white. So `snapshot_ui` refuses `appearance` whatever its value, naming the default, and `DevAppearance.swift` sets `NSApp.appearance` from `main.swift` before `NSApplicationMain`. No Apple launch argument gives a dark app on a light system (`-AppleInterfaceStyle` was ignored both ways), hence a dev default. It is not in `AppDelegate.swift` because a line added there moved the `runModal` lines `inventory.json` pins by line and H1 failed with 11 problems. (orig V1 record Q3 as qualified; V3 record "Measured after the review", "Review")
- **The inspector's tab is picked through the strips' own click paths.** V3 added `select_inspector_tab` (the road map hoped for no app change) through `InspectorViewController.select(_:)` and `selectClipSubTab(_:)`, so a capture is what a click shows; a mutant choosing the sub-tab directly on the pane answered `clip` while the dump showed the wrong section (M6, T3). The `recorder` window kind is found by controller class in `NSApp.windows`, never `.shared`, which would build the panel; the `.shared` mutant accepted a capture it should have refused (M7, R1). (orig V3 record)
- **The screen catalog is prose in the repo, captured per look on its own instance.** `designs/screens/` holds one file per screen: a JSON front block (fixture, MCP steps, captures) and prose written after the captures were read. `tools/proof/screens.py` runs the catalog once on an instance launched light and once dark, never passes `appearance`, and fails a screen whose capture answers another look; a screen whose steps fail is a scored failure, never a gap (screen-file mutants M1–M5 each fail exactly their screen). The recorder panel is the last screen and the instance is stopped straight after its captures. Putting the panel up used to bring Reelcut to the front with Record on Return; since #137 (spec §11, "The recorder panel takes key only from an active Reelcut") a panel shown from the background leaves Reelcut inactive (`v3_tools.py`'s R3), but an instance that is active when New Recording… runs still gets a key panel with Record on Return, and the script cannot hold its child inactive. (orig Phases V3; V3 record)

## Known limits

- **The flag-off path is compiled only by `make dist`**, not by `make typecheck` (V-1's accepted risk).
- **`AgentServer+Snapshot.swift` is at 400 lines**, the new-file cap: the next addition pays a toll first.
- **A capture is a picture of the chrome.** Pixel claims about the video stay with `render_frame` (V-3), and captures carry the display's colour profile, not sRGB.
- **Two refusals are named but unreachable over MCP:** a windowless document (no tool makes one; V2a's C4, V3's T4) and, for `snapshot_ui`, a file panel is refused rather than captured.
- **What `perform_menu_item` will not run:** the sixteen AppKit-owned items and the two `modal` ones (Allow Agent Connections, New Project), and every AppKit-injected leaf the inventory does not read (Writing Tools, Dictation, the Window menu's window items, …: V2b's N1 counted 172 live leaves against 145 inventoried). A sheet's own buttons are never pressed except the Cancel.
- **The spike's W4a–c depend on the display scale** (at scale 1 the overlay's core holds no translucent pixels and they pass), so the probe places its windows on a scale-2 screen and skips W4a–c by name without one.
- **The catalog has been captured on one host**: a Dark system, scale 1, one external display. On it, `-RCDevAppearance light` differs from a forced-aqua launch only in the timeline's alternate lanes and scroller (97 786 px); which a real Light host matches is unmeasured (#139). The demo's Video track sits below the timeline's visible 300 pt in every editor capture.
- **The offscreen harness is kept** for byte-identical proofs of states a package can describe; its preview well is also the canvas background.
- **`perform_menu_item`'s settle is kept, though nothing known needs it** (owner's decision, 2026-09-30, #135). The answer waits for five agreeing reads of the sheet, the modal window and the visible windows (20 ms apart, at most 3 s) so a sheet that arrives after the action returns is in it. `v2_menu.py` L1 reaches the one known late sheet (the reverse-render progress sheet) and passes with the settle removed too, because that sheet is queued before the answer's own main hop. So no row fails without the settle: it is an untested safety margin of about 0.1 s per call, in the dev tools only (Distribution has none, spec §11 V-1).
