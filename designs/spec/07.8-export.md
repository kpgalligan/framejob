# 7.8 Export

Presets (`rc_export_presets`), in menu order, are ENCODINGS — a container
and a codec, with no size of their own: `h264` H.264 (MP4), `hevc` HEVC
(MP4), `hevc_alpha` HEVC with Alpha (MOV), `hevc_10bit` HEVC 10-bit (MP4),
`av1` AV1 (MP4), `av1_webm` AV1 (WebM), `vp9_webm` VP9 (WebM), `vp9_alpha_webm` VP9 with
Alpha (WebM), `prores_422` ProRes 422 (MOV), `prores_4444` ProRes 4444 (MOV), `audio_m4a` Audio only (M4A),
`audio_wav` Audio only (WAV), `audio_aiff` Audio only (AIFF), `gif`
Animated GIF, `apng` Animated PNG. The size is a separate choice whose
default is the document's own size, so a 1440p or a vertical project does
not come out at 1920 × 1080 because a row said so; the two image formats
are the exception and carry the cap argued below. **The first row of each
list is the default.** The export sheet opens on the remembered choice
(`ExportChoice.remembered`, written on Export or Add to Queue), and on
`h264` with its Size popup on the first row only when none is remembered;
the Size rows are `rc_export_sizes(project, preset)`, which lists
the sizes offered for that document and format: the document's size
(`document` — "Document size", not "source size": §4.3's source size is a
media item's, and this row renders at the canvas), or for an image format
its cap (`preset`) with the document's size second; then the standard
sizes fitted to the document's aspect, largest first — `2160p` (named 4K),
`1440p`, `1080p`, `720p`. The number is the SHORT edge, because "1080p
ultrawide" is 2560 × 1080 and "1080p vertical" is 1080 × 1920 — the short
edge is the number people mean — and the long edge is the document's,
scaled to match and rounded to the nearest even integer, since H.264 and
HEVC need even dimensions and a size the writer would quietly change is
not one the sheet may offer. The same holds for the Document row and for
any size asked for (§11 G-33): on the rows that need even dimensions —
every row AVFoundation writes but `prores_4444` — an odd edge is resolved
one pixel SMALLER, which is the size the writer always wrote, so on a
canvas with an odd edge that row's numbers are the canvas evened and its
name is "Document (even)"; `prores_4444`, `gif` and `apng` keep an odd
edge, and theirs stays "Document size". A row may repeat an earlier row's
numbers —
a 1920 × 1080 document's `1080p` is its own size — and is listed anyway,
because an id is the `export` tool's vocabulary and has to mean the same
thing on every document; the sheet hides a row whose numbers an earlier
row already has, keeping the name that says more. On an image format
every row's numbers are the canvas fitted inside that box, never upscaled
(below). The audio-only preset lists the same rows as `h264` and the sheet
disables the control. The agent's `export` takes the same ids in its
`size`, or an explicit `[width, height]` (the sheet's "Custom…").
`rc_export_settings` resolves a preset plus overrides (size, fps, range =
whole or in/out, `optimize_for_network`, the two bitrates below, the two
loudness figures below them, `av1`'s and `av1_webm`'s `encoder_speed` and
`audio_wav`'s and `audio_aiff`'s `audio_bits`, and the three audio rows'
`stems`) to concrete settings, no size override meaning the preset's cap where it has
one and the canvas otherwise — and to the size the file will have: the
width and height it answers are evened as above on the rows that need it
and fitted on the image formats, whether they came from the canvas, a row
or a custom size. Each preset AVFoundation can write still
carries an `AVAssetExportSession` preset name
(`AVAssetExportPresetHighestQuality`, `…HEVCHighestQuality`,
`…HEVCHighestQualityWithAlpha`, `…AppleProRes422LPCM`,
`…AppleProRes4444LPCM`, `…AppleM4A`, and `av1`'s, `av1_webm`'s,
`vp9_webm`'s and `vp9_alpha_webm`'s `…Passthrough`) — that
mapping is what names the
codec and tier, and `avf_preset: null` is how a preset says AVFoundation
cannot write it at all. Since phase 5 the field means **only** that: the
name is a record, not an instruction, because `null` is what routes an
export to the ImageIO writer and AVFoundation has no `AVAssetExportPreset`
for LPCM, so `audio_wav` and `audio_aiff` repeat `audio_m4a`'s name — the
closest true statement available, "an audio-only file AVFoundation
writes". A null there would hand a WAV to `ImageSequenceWriter` and report
a format this table advertises as an unsupported file type. But
**nothing runs a session any
more**: M2's `AVAssetWriter` path REPLACED it rather than joining it, for
the reason the whole design exists — two writers would make the chapter
track, the explicit bitrates and the output size conditional on which one
happened to run, and leave two answers to "what did the file end up as".
`ExportWriter` reads the composition through one `AVAssetReader` per
output (the video composition and the audio mix each on its own, §11 #378)
and writes video, audio and a chapter track (an `AVAssetWriterInput` text track
associated `AVTrackAssociationTypeChapterList`), reporting `progress` on
the same timer the sheet already polled. GIF and APNG take the ImageIO
path instead, frame by frame over `Exporter.renderFrame`. **The one
exception is WebM (§11 CX-15 (2)):** `AVAssetWriter` writes no WebM, so
`Exporter.pipeline` sends a `webm` container (`av1_webm`, `vp9_webm`,
`vp9_alpha_webm`) to
`ExportWebMWriter`, a second
`ExportPipeline` that is `ExportWriter`'s WebM half and nothing more — the
same reader outputs (`ExportWriter.videoReadOutput` / `audioReadOutput`), the
same `ExportEncodePump`, gain, #337 end, chapter partition
(`ExportChapter.partition`), size and rates — so each of those is still one
decision, and only the container differs.

**Quality.** `video_bitrate` and `audio_bitrate` are overrides in bits per
second, strictly positive; a zero, a negative, a fraction or a non-number
is an error naming the value. No preset carries a default and neither key
appears in the resolved settings unless it was asked for: on the session
path the preset name IS the bitrate ladder, and on the writer path
VideoToolbox's size-derived rate beats any constant the table could hold.
An absent `video_bitrate` therefore means "the encoder decides", which is
exactly what `ExportSettings.videoBitrate == nil` says on the Swift side. An
absent `audio_bitrate` on an AAC row is 192 kbps (stereo, 48 kHz), so only
the video rate is left to the encoder.

**ProRes 4444, and what `alpha` means.** One row beside `prores_422`
(road map 2, phase 7) for the file whose next reader is another
application rather than a viewer: a master or an intermediate — a lower
third cut over somebody else's footage, a screencast going back into a
compositor — where the picture has to arrive with its transparency
intact. It shares 422's container, its colour and its
editing-master posture (no `moov` rewrite: nothing streams a ProRes) and
differs in exactly one thing, which is the whole reason it is a row: 422
cannot carry alpha at any bitrate, and neither can the `h264` or `hevc`
row — neither has an alpha channel in the profile `ExporterWriter` writes
for it, so a transparent canvas exported through one of them is a picture
flattened onto black with no way back (`hevc_alpha`, below, is the
delivery row that keeps it). It sits AFTER 422 because a row's position
is an invitation and most exports of a finished timeline want the smaller
file. Its session name is `…AppleProRes4444LPCM` and is NON-null for the
LPCM rows' reason: a null is the ImageIO writer's cue, and a `mov`
handed to `ImageSequenceWriter` would be refused as an unknown image
container.
Its frames are written STRAIGHT (§11 G-35, amended by PR-3):
`ExportWriter`'s video pump un-premultiplies the compositor's premultiplied
64RGBAHalf in place, in float (s = min(1, c/a) for a > 0), fills each
transparent pixel within 4 px of a visible one with the nearest one's
colour, and labels each buffer `StraightAlpha`, which the encoder writes
into the file — so the file's label is true and a reader, Frame Job
included, composites it to the right colour.

**HEVC with alpha.** One row directly after `hevc` (§11 G-33) for the
DELIVERY file that keeps a transparent canvas — a title or a lower third a
web page or another editor plays over its own background, at HEVC's size
where `prores_4444` is a master. `ExportWriter` writes
`AVVideoCodecType.hevcWithAlpha` into a QuickTime movie, the container
AVFoundation writes that codec into (an `.mp4` refuses it), with AAC
sound, HEVC's Quality tiers and bit-rate controls (the sheet reads the
codec by its `hevc` prefix), HEVC's default rate, and
`optimize_for_network` off unless asked. The compositor's premultiplied
64RGBAHalf is first rounded to 8-bit premultiplied BGRA (round(v·255),
exact for every k/255) in a pooled 32BGRA buffer (§11 PR-3), then
straightened on the way to the encoder by G-35's 8-bit rule, unchanged —
so this row's encoder input is what it was before the 16-bit compositor —
and one compression key says what it then is
(`kVTCompressionPropertyKey_AlphaChannelMode`, straight); there is no
alpha-quality key and no profile key. The frame is even-sized
as `hevc`'s is, so an odd edge resolves one pixel smaller, and `alpha` is
true, so the shape rule below reaches it. ffprobe reports `hevc`, `hvc1`,
`yuv420p` for this file exactly as for a plain HEVC one: its alpha can be
read only off a decoded frame, which is what `hevc_alpha_proof.py` does.

**HEVC 10-bit.** One row after `hevc_alpha` (§11 PR-3; G-33 keeps
`hevc_alpha` directly after `hevc`) for the DELIVERY file that keeps a
10-bit source's depth: `hevc`'s MP4 in every core field but the id, the
name and the codec, `hevc_10bit`. `ExportWriter` maps that codec to
`AVVideoCodecType.hevc` with `kVTProfileLevel_HEVC_Main10_AutoLevel` and
hands the encoder the compositor's 16-bit frames as they are (`frameForm`
asks the codec NAME first, because `hevc` and `hevc_10bit` share the codec
type). It is even-sized, carries no alpha, and takes HEVC's Quality tiers
and default rate (the `hevc` prefix). ffprobe reports `hevc`, `Main 10`,
`yuv420p10le` and an `mp42` major brand (`precision_proof.py` T1), and the
precision road map's 10-bit ramp comes through it at less than half the
error it shows through `hevc` (T2; the figures are in
`designs/adr/precision.md`).

**AV1 (codec-export C1, C2, §11 CX-1, CX-2, CX-9, CX-10, CX-12, CX-13, CX-14).** One row after
`hevc_10bit`: `av1`, "AV1 (MP4)", MP4 with AAC, 10-bit Main 4:2:0 in every project,
even-sized, no alpha. Its picture is encoded by the bundled SVT-AV1 (CX-4), not
VideoToolbox, and the row says so in a field of its own, `writer`
(`"svt_av1"`); `avf_preset` is `AVAssetExportPresetPassthrough`, a record
only, because AVFoundation still writes the container, so the row is routed
and sized as every AVFoundation row is and `avf_preset: null` keeps meaning
ImageIO. `rc_export_presets` gives the row and `av1_webm` (below) alone
`writer` and `encoder_speeds` (`["faster", "balanced", "smaller"]`), and their
resolved settings alone end with `writer` and `encoder_speed` — the override
(`faster`, `balanced`, `smaller`: SVT-AV1's presets 8, 6 and 4, CX-2),
`balanced` when absent; a word that is not one of the three is refused on
any row (`export encoder_speed must be "faster", "balanced" or "smaller",
not …`) and a speed on any other row is refused naming it (`{id} has no
encoder speed; encoder_speed applies to av1 and av1_webm`). Every other row's settings
are the text they were. The frames: the reader's 64RGBAHalf frames are
scaled on the GPU (`MPSImageLanczosScale`) when the export size is not the
canvas — fitted with black bars, or filling a frame within a pixel of the
canvas's shape, G-33 (c) — and converted by `ExportI010.metal` to video-range
10-bit I010 through the picture's matrix (`ExportAV1Picture`, CX-14 (3): BT.709's
for `sdr`, BT.2020's for `hlg` and `pq`; Y = round(64 + 876·Y′), chroma
clamp(round(512 + 896·C′), 0, 1023) of the mean of each 2 × 2 block, premultiplied
RGB as it is, so a transparent canvas lands on black);
a serial encode queue owns the encoder (`ExportEncodePump`), with progress
counted by frames submitted, the cancel flag read before each read, send
and append, and the end of stream drained before `markAsFinished`. SVT-AV1
runs capped CRF (CX-13): the cap is `video_bitrate`, or HEVC's 0.07 bits
per pixel per frame when none is asked, set as `max_bit_rate`, and the CRF
is the one CX-13's calibration gives the speed at the cap's bits per pixel
per frame — matching or beating HEVC at that rate. The cap is soft (SVT's
default 50 % overshoot): a file usually averages far less than the rate,
and detailed footage was measured up to 1.254 × it; with a closed GOP and a
keyframe at least every 2 s (`intra_period_length` = ⌊2·fps⌋ − 1), and writes the
picture's primaries, transfer and matrix in video range into its sequence header
(CX-14 (4): `sdr` 1/1/1, `hlg` 9/18/9, `pq` 9/16/9). The
container bytes are the core's (`rc_av1_*`, CX-12 (4)): the `av1C` record
built from SVT's sequence header OBU, each packet's temporal delimiters
stripped, and the finished file's `ftyp` rewritten in place so `av01` is a
compatible brand (`isom mp41 mp42` → `isom av01 mp42`); a file whose `ftyp`
cannot take it fails the export. The packets go to a passthrough
`AVAssetWriterInput` whose format description holds the `av1C` and the same
colour tags (the `colr` box), one sample each; on `pq` alone HD-5's fixed HDR10
metadata is written twice, as SVT-AV1's HDR_MDCV and HDR_CLL metadata OBUs on
each KEY_FRAME and as the `av01` entry's `mdcv` and `clli` boxes from
`OutputTransform`'s two blobs, the same values (CX-14 (5)); the writer reads the sync
samples from the bitstream's key frames, so the pump attaches none.
SVT's own log goes through its callback: warnings and errors as `SVT-AV1: …`
lines in the system log, nothing else. **On an M1 or M2 Mac Frame Job cannot
play or re-import its own AV1 file, and QuickTime cannot either (CX-10):**
those Macs have no AV1 decoder, and #216's refusal stands.

**AV1 in WebM (codec-export C3, §11 CX-6, CX-7, CX-15).** `av1_webm`, "AV1
(WebM)", directly after `av1`: the same encoding — `writer` `svt_av1`, the
same `encoder_speeds`, CX-13's cap and CRF table, CX-14's I010, CICP and PQ
HDR10, one of the HDR rows, even-sized — in a WebM the core writes, with Opus
sound (container `webm`, `org.webmproject.webm`; `optimize_for_network`
defaults false and does nothing there, as on WAV; a speed on any other row is
refused `{id} has no encoder speed; encoder_speed applies to av1 and
av1_webm`). `Exporter.pipeline` gives it `ExportWebMWriter` (above), whose
video pump is `ExportEncodePump` into an `ExportWebMPacketSink` and whose
audio pump reads the mix, gains it, places it at its stamps (zeros for a
gap, a covered head cut: `ExportAudioEnd.align`), cuts it at the range
(`ExportAudioEnd`) and encodes it with AudioToolbox's Opus (`ExportOpusEncoder`:
48 kHz stereo, 20 ms packets behind a 960-frame FIFO fed by each buffer's
bytes, 192 kb/s by default or
`audio_bitrate`/the Quality tier snapped to the converter's rates, the
pre-skip `primeInfo.leadingFrames`). **The writer is the core's**
(`rc_webm_*`, `webm_writer.rs`): EBML DocType `webm` 4/2; a SeekHead patched
over a reserved Void; Info at millisecond timestamps with the duration and
"Frame Job"; track 1 `V_AV1` with the `av1C` as CodecPrivate, DefaultDuration
and Colour (the sequence header's CICP, Range 1, BitsPerChannel 10, and on
`pq` MaxCLL, MaxFALL and MasteringMetadata from `OutputTransform`'s blobs);
track 2 `A_OPUS` with OpusHead v1, CodecDelay round(pre-skip / 48 kHz) and an
80 ms SeekPreRoll; one chapter edition (`ExportChapter.partition`, language
`und`); block times rounded half up to the millisecond; a Cluster at each
video key (and before 32,767 ms), each key-started Cluster a CuePoint; the
Cues, the SeekHead and the Segment's size written at finish. The core
queues each declared track and writes the earliest head only while every
track not ended has one, so the two pumps never wait on each other (the
Opus track at worst, about 1.4 MB a minute, CX-15 (4)). **The tail:** the
encoder's finish feeds pre-skip frames of silence before its end of stream;
whole surplus packets are dropped and the last carries the rest as
DiscardPadding, so the decoded sound is #337's length exactly, and a
negative surplus fails the export (`The audio could not be encoded to its
exact length.`). **A composition with no audio track is a silent movie**:
no audio track in the file. A cancelled or failed export removes the hidden
sibling it wrote and leaves the path as it was (§11 #531).
**One reader per output (CX-15 (2)):** the video composition output and the
audio mix output each have an `AVAssetReader` of their own, so neither read
can be starved by the other pump's stop, and each pump cancels its own reader
after its own last read (G-17's rule). G-17's starvation is closed for WebM
(F1–F3: a failure on either pump, or a cancel while the audio read is held,
ends the export within 10 s, and the readers' log line names a shared reader).
It is closed on `ExportWriter` too, by the same rule (§11 #378; F1–F4 of
`export_readers_proof.py`).

**VP9 in WebM (codec-export C4, §11 CX-3, CX-8, CX-16).** `vp9_webm`, "VP9
(WebM)", directly after `av1_webm`: VP9 from the bundled libvpx v1.17.0 in the
same WebM, through the same `ExportWebMWriter`, Opus, chapters, range, silent
movie and #337 length. `rc_export_presets` gives it `"hdr": true` and
`writer` `"libvpx"` and no `encoder_speeds`; its settings end with `writer`
and carry no `encoder_speed` (libvpx has one speed, CX-3: good deadline,
cpu-used 4, row-mt), so `encoder_speed` on it is refused `vp9_webm has no
encoder speed; encoder_speed applies to av1 and av1_webm`, and the sheet's
Speed row is disabled on it. `ExportEncodePump` picks `VP9Encoder` by
`writer` (`ExportVideoEncoder`, the protocol both encoders answer). **The
depth is the picture's (CX-16 (3)):** `sdr` is Profile 0, 8-bit I420
(`framejob_export_i420`: Y = round(16 + 219·Y′), chroma clamp(round(128 +
224·C′), 0, 255), BT.709), and `hlg` and `pq` are Profile 2, 10-bit I010
(`VPX_IMG_FMT_I42016`, BT.2020 non-constant), libvpx told the colour space and
studio range. VP9's bitstream carries no transfer, so **the WebM `Colour` is
the only transfer label** (CX-8): the picture's CICP (`sdr` 1/1/1, `hlg`
9/18/9, `pq` 9/16/9), Range 1, BitsPerChannel 8 or 10, and on `pq` HD-5's
MasteringMetadata, MaxCLL and MaxFALL. Track 1 is `V_VP9` with **no
CodecPrivate** (optional in Matroska's VP9 mapping; #216-R's reader builds
`vpcC` from the first keyframe). A keyframe at least every 2 s (`kf_max_dist`
⌊2·fps⌋), the block's key flag libvpx's `VPX_FRAME_IS_KEY`, a 25-frame lag
with alt-refs packed into superframes so each packet is one shown frame. The
rate is capped constant quality (CX-16 (7)): `VPX_CQ` at a CQ level from a
table per depth calibrated against `hevc` and `hevc_10bit` at the cap's bits
per pixel per frame, the cap CX-13 (2)'s as the target, libvpx's own 25 %
overshoot. libvpx's macro and variadic call go through
`app/Bridging/FrameJobVPX.h`. Apple silicon decodes VP9, so Frame Job
re-imports its own `vp9_webm` on any M1 or later.

**VP9 with alpha in WebM (codec-export C5, §11 CX-17).** `vp9_alpha_webm`,
"VP9 with Alpha (WebM)", directly after `vp9_webm`: the transparent movie
Chrome and Firefox play (Safari's is `hevc_alpha`). `rc_export_presets` gives
it `writer` `"libvpx"` and no `encoder_speeds` and **no `hdr`**: it is always
8-bit Profile 0, BT.709, so an HLG project writes its SDR version (settings
`color` `sdr`) and `hlg`/`pq` are refused in the 8-bit sentence. Its `alpha`
is true, so G-33's shape rule binds it (`Exporter.settingsRefusal` asks it
before anything is queued, §11 #470, and `ExportWebMWriter` calls
`ExportWriter.checkAlphaSurvivesTheSize` as the backstop). The pump
straightens each 64RGBAHalf frame in place first (G-35 in float, PR-3's
`prores_4444` pass, `ExportStraightAlpha.straighten`; G-35's sentence when it
cannot), converts the straight colour to BT.709 video-range I420 and the
alpha, by `framejob_export_alpha8`, to a second 8-bit picture whose Y is
round(255·clamp(a)), full range, over a constant chroma of 128, and encodes
both with `VP9AlphaEncoder`: two `VP9Encoder`s on the encode queue, the
picture exactly `vp9_webm`'s 8-bit (capped CQ, the cap and `video_bitrate`
its alone) and the alpha `VPX_Q` at `VP9Encoder.alphaCQLevel(pixels:)` in full
range: a level per size band, the band at or below the picture's pixels (34
from 640 × 360 and below, 38 from 1280 × 720, 40 from 1920 × 1080, 46 from
3840 × 2160), each the highest that kept the moving disc's worst alpha frame
at 48 dB or more at that size (CX-17 (6) as amended). Both force a key on every frame whose index is a multiple of
⌊2·fps⌋ with `kf_min_dist` = `kf_max_dist` = it, and a packet is answered
only when both streams have that frame, a pts or key disagreement failing the
export in its own sentence. The layout's `alpha_mode` makes the TrackEntry
carry `MaxBlockAdditionID` 1 and its Video `AlphaMode` 1, and each video
block, added through `rc_webm_add_video_with_alpha`, is a BlockGroup: the
Block, BlockAdditions{BlockMore{BlockAddID 1, BlockAdditional = the alpha
frame}} and, on a non-key only, a ReferenceBlock (the previous video block's
ms less this one's). Only a libvpx decoder reads the alpha (ffmpeg's native
`vp9` ignores it). **Re-imported, it keeps its colour and loses its alpha**
(CX-17 (7)): the rewrap copies the Block and not the BlockAdditional, and
Apple's VP9 decoder has no alpha — an accepted limit.

**Encoder memory and the estimate (codec-export C6a, §11 CX-18).** A
bundled-encoder export — settings with a `writer` — is booked in one
app-wide, main-thread ledger (`ExportEncoderLedger`) from just before its
`Exporter.export` call to its finish: the Export Queue's running job and
every Export… progress sheet's. Its cost is its resident peak from
`ExportEncoderCosts.memory`, keyed by row, AV1 speed and bit depth (10 on
`svt_av1`; on `libvpx` 10 for `hlg`/`pq`, else 8), measured at 1920 × 1080
and 3840 × 2160 by `tools/proof/encoder_memory_measure.py` and read at the
export's pixels (proportional below 1080p, linear through both points above,
extrapolated past 4K); a writer row with no entry costs the whole budget.
The budget is a quarter of physical memory (G-37's share). The queue stays
one job at a time, but `start()` launches the first waiting job the ledger
admits — nothing booked, or the booked costs and its own within the budget —
passing over a held encoder job (an AVFoundation job is always admitted), and
re-runs on the ledger's change notification, so a sheet's finish wakes it.
A held job's `message` is "Waiting for memory: AV1 and VP9 exports running
now hold about X GB of the Y GB this Mac allows them, and this one needs
about Z GB.", its row's status line (truncated at the tail where it does not
fit), the last line of the row's tooltip, and `export_status`'s `waiting`. A
sheet is counted but never held. The sheet's summary gains a second line on a
writer row, "Estimated time: about …": `ExportEncoderCosts.time`'s setup
seconds plus the range's frames times its per-frame seconds at the size
(5 s steps under a minute, whole minutes under an hour, then "h … min"),
C6b's idle three-run medians on real 4K footage (CX-18's amendment); no
estimate on an AVFoundation row, nor when the rate cannot be stepped and the
range has no frame count.
