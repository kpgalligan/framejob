# 7.10 Rust module map

Crate `framejob_core`, `crate-type = ["staticlib", "rlib"]`, deps `serde`,
`serde_json`, `serde_path_to_error` (the path a patch refusal names),
`tiny_http` (agent), and `graphic` (road map 10's motion-graphics engine, a
path dependency named by `ffi_graphic.rs` alone, G-2). Soft cap 600 lines per module; a new
concern is a new module with its own `impl Project` block.

| Module | Owns |
|---|---|
| `lib.rs` | declarations and re-exports only |
| `model.rs` | the §5.2 types and serde derives, and the serde defaults that say what an absent key means — the schema's SHAPE, and nothing else |
| `model_props.rs` | the §5.2 per-clip property types — `VideoProps`, `Crop`, `Shadow`, `ColorAdjust`, `Chroma`, `Filter`, `Reflection`, `BlendMode`, `AudioProps`, `Compressor`, `Duck`, and their enums, with their defaults: the schema's VOCABULARY where `model.rs` is its shape. Cut out under the size rule (road map 2, phase 2) and re-exported whole by `model.rs`, so every `crate::model::X` path still resolves. It has since paid the same rule THREE times itself, every time BEFORE the phase that owed it took anything on: the region types went to `model_regions.rs` in phase 3c, the text vocabulary to `model_text.rs` in phase 6 and the shape vocabulary to `model_shape.rs` in road map 5's E2, and it re-exports all three, so no path anywhere changed any time |
| `model_regions.rs` | the boxes drawn ON the picture — `Spotlight`, `ObscureRegion`, the `SpotShape` both are drawn with and the `MAX_OBSCURE` budget on the second. One concern, not three adjacent ones: they share one coordinate frame (`x`/`y` the region's CENTRE, an offset in SOURCE pixels from the centre of the layer's CROPPED rect; `width`/`height` its size in the same pixels — which is what carries a region with its layer through scale, move and rotation) and one shape enum. Cut out of `model_props.rs` under the size rule (road map 2, phase 3c) and re-exported whole by it, so every `crate::model::X` path still resolves; the FIELDS holding them (`VideoProps.spotlight`, `VideoProps.obscure`) stay with the video group |
| `model_text.rs` | the text vocabulary — `TextProps`, the `TextAlign` and `TextVAlign` it is placed by, the `Outline` and `Backdrop` drawn with it, and the `TextAnimation` and `TextAnimationKind` that reveal it. Cut out of `model_props.rs` under the size rule (road map 2, phase 6) and re-exported whole by it, and cut HERE because text is the one property group the model cannot MEASURE: every other group is quantities the core bounds, interpolates and solves against, while only the platform can lay a string out and the size comes back the other way through a cache (§5.3, §11). `TextAnimationKind`'s declaration order is NOT load-bearing — the recipe carries a reveal's kind by NAME — where `ObscureKind`'s and `BlendMode`'s are shader discriminants; the JSON spelling of every variant is, so a rename needs a migration step |
| `model_shape.rs` | the shape vocabulary — `ShapeProps`, the `ShapeKind` it draws, the `Stroke` around it, and the `Gradient`, `GradientKind`, `GradientStop` and `MAX_GRADIENT_STOPS` that fill it. Cut out of `model_props.rs` under the size rule (road map 5, E2) and re-exported whole by it, and cut HERE because it is `model_text.rs`'s seam read a second time: shape and text are the two sources the model only DESCRIBES, drawn on the CPU and keyed by the recipe's content hash, where everything left in `model_props.rs` is read straight into the compositor's uniform block. Nothing here is ever a shader discriminant — `GradientKind` may gain a kind at the END and nothing derives a number from the order, where `BlendMode`'s order IS the discriminant |
| `model_motion.rs` | the motion vocabulary (format version 8, road map 5's E2) — `Motion` and the `MotionEdge`, `MotionDuring`, `EdgeMotion` and `DuringMotion` it is made of. Its own module for a seam rather than for room: every other member of the video group is a quantity the compositor reads more or less straight, while these five say only what a clip should DO and the placement that comes out of them is computed at render time by `motion.rs`. Re-exported whole by `model_props.rs`; neither enum's declaration order is load-bearing, and both are closed |
| `model_words.rs` | the word-caption vocabulary (format version 9, road map 8's W1b; §5.2, §11 W-1 to W-6) — `TextCase`, `Word`, `WordMode`, `ActivePill` and `WordStyle` (with `template()` for `patch.rs`), re-exported through `model_props.rs` like the other vocabularies; the FIELDS stay on `TextProps`. And the two facts every writer of `text.words` shares, `pub(crate)` and named directly by their callers: `token_count` (`split_whitespace` — the core is the one counter) and `rebase_words` (the one saturating subtraction `trim_start`, `roll`, `add_transition`'s handle form and `split`'s second half make). Format version 12 (§11 W-12) added three looks as keys, each off by default: `ActivePill.glide`, `WordStyle.active_fill` and `WordStyle.pause_dim` (0–1, range-checked in `props_check.rs`) |
| `model_look.rs` | the look vocabulary (format 15, §11 GR-7) — `LookKind` (the eight, `warm` to `black_white`, then `lut` (GR-8); its declaration order is the gallery's and the menu's, append only; `BUILT_IN` the eight), `Look` (`kind`, with no default, `media`, a LUT's media id, and `amount`, 1 by default), `SplitTone`, `LookDefinition` and `LOOK_DEFAULT_AMOUNT`, re-exported through `model_props.rs`; `LookKind::definition` is each built-in look's Color, Light and split-tone values (`None` for `lut`) — DATA the recipe publishes and the compositor bakes. The FIELD `VideoProps.look` stays in `model_props.rs`, written only when a clip has a look |
| `model_grade.rs` | tier 2's grading vocabulary (format 16, §11 GR-11) — `Wheels {lift, gamma, gain}`, each a `Wheel {x, y, master}`, `WHEEL_MAX` and `WHEEL_RIM_TOLERANCE`, re-exported through `model_props.rs`; each key is written only when not 0 and a neutral wheel not at all. The FIELD `VideoProps.wheels` stays in `model_props.rs`; `actions::wheels_json` writes all nine for the evaluator, the patch template and the recipe. Format 17 (§11 GR-12) adds `Curves {master, red, green, blue}`, each an optional list of 2–16 `CurvePoint`s (`[x, y]`), `CURVE_POINTS_MIN` / `CURVE_POINTS_MAX`, `IDENTITY_CURVE` and `curve_is_identity` (every y = x from x 0 to x 1); an identity channel is not written and `drop_identities` removes one. The FIELD `VideoProps.curves` stays in `model_props.rs`. Format 20 (§11 GR-32) adds `Curves.hue_hue` and `.hue_sat` (`[hue, value]` points, 0 ≤ hue < 360), `CurveDomain` (`Tone`, `HueShift`, `HueGain`: each channel's identity, neutral and value range, `named()` and `named_mut()` giving each channel's), `HUE_SHIFT_MAX`, `HUE_GAIN_MAX`, `IDENTITY_HUE_SHIFT` and `IDENTITY_HUE_GAIN`; a hue curve whose every value is its neutral is the identity, whatever its x's. Format 18 (§11 GR-13) adds `Qualifier {hue, saturation, luma, invert}` — `HueRange {center, width, softness}` in degrees, `LevelRange {low, high, softness}` in 0…1, each `None` when off, `HUE_TURN` and `HUE_SOFTNESS_MAX` — written only when not neutral; the FIELD `VideoProps.qualifier` sits after `curves`, and it acts only on an adjustment clip. Format 21 (§11 GR-35) adds `Qualifier.blur` (0…1, written only when above 0, after `invert`) and `QUALIFIER_BLUR_MAX`; `is_neutral` counts it, so a blur alone is kept |
| `actions_curves.rs` | the curves' helpers for action evaluation (§11 GR-12, GR-34), beside `actions.rs` because that file is near its cap: `curves_json` (all six channels, an absent one as its domain's identity, `IDENTITY_CURVE` or the hue identities, §11 GR-32, for `video_json`'s callers — the evaluator, the patch template and `split`); `align_identity_curves` (on the two states' `video.curves` before the lerp: an identity channel meeting a curve of another count takes that curve's x's, its ends at `[0, 0]` and `[1, 1]` on a tone curve and every value the neutral on a hue curve, so a grade animates from or to neutral); `CurveBlend` and `curve_blends` (the channels whose held and clamped end curves are both non-identity with different counts, with the eased t, strictly inside 0…1: `Evaluated.curve_blends`); and `blended_curves_json` (`curves_json` with each blended channel as `{from, to, t}`, for the recipe layer and `clip_state` only) |
| `actions_qualifier.rs` | the qualifier's two rules for action evaluation (§11 GR-13, GR-35), beside `actions.rs` because that file is near its cap: `qualifier_json` writes a qualifier with its `blur` present even at 0, which `video_json` uses for a non-neutral one so the blur animates from 0; and `align_hue_center`, before the lerp, moves the action's TARGET hue centre by ±360 when the two states' centres are more than 180° apart, so the centre animates the short way round (350 → 10 through 0); `actions_clamp.rs`'s `clamp_qualifier` brings the lerped centre back into [0, 360). Exactly 180 apart goes linearly; an ended action's end is not touched |
| `model_canvas.rs` | the canvas's blending (format version 24, §11 GR-18, HD-16) — `CanvasBlending`, `encoded` or `linear`, with `is_encoded` for the `skip_serializing_if` on `Canvas.blending`; re-exported by `model.rs` (a file of its own so `model.rs` stays clear of the cap). The FIELD `Canvas.blending` stays in `model.rs`, written only when `linear` |
| `model_matte.rs` | the matte vocabulary (format version 14, §11 MT-1) — `TrackMatte`, `none` to `luma_inverted`, re-exported through `model_props.rs`; the FIELD `Track.matte` stays in `model.rs`, written only when not `none`. Its declaration order is a shader discriminant (MT-3), append only, like `BlendMode`'s |
| `model_graphic.rs` | the graphic vocabulary (format version 10, road map 10's G2a; §5.2, §11 G-3, G-4, G-12) — `GraphicProps` (`name`, `width`, `height`, `in`, `length`, `props`) and the `GRAPHIC_MIN_SIDE` / `GRAPHIC_MAX_SIDE` / `GRAPHIC_MAX_PROPS` bounds, re-exported through `model_props.rs`; the FIELD `Clip.graphic` stays in `model.rs`. And the checks every writer of one shares, `pub(crate)`: the module name rule, the side bound, a schema's eight sentences and the props checked against it (or for shape only without one), the key count on the STORED map, and `normalise_color`. The engine crate's sentences and limits are COPIED here, because no module of the model may name it (G-2); a props map is only ever changed by `insert` and `shift_remove`, because `serde_json`'s `remove` swaps the last key into the hole under `preserve_order` |
| `recipe_graphic.rs` | a graphic clip's own timeline and its layer (road map 10's G2b; §7.3, §11 G-9): `effective_length` (`graphic.length`, or `in + duration` when `null`) and `graphic_advanced` (`in` moved through `source_window.rs`'s `in_advanced` at speed 1, never below 0), the ONE equation the writers — `trim_start`, `roll`, `split`'s second half and `add_transition`'s head move `in`, `split` pins both halves' `length` — and the reader share; `graphic_resnapped`, which every re-snap through `frame_grid.rs` writes (`in` to the nearest frame, ≥ 0; a set `length` to the nearest frame, at least one; §11 G-18); and `graphic_source`, the layer's `{kind, name, hash, frame, ctx, props, props_json, ctx_json}` and `[width, height]`, its hash over everything `render` is called with — the two `_json` keys (road map 10's G3b) the serialized text of `props` and `ctx`, which the app hands the engine untouched. Here rather than in `model_graphic.rs` or `source_window.rs` because both stand at their caps; the edit modules importing it follow `edit_split.rs`'s reading of `actions` and `source_window` |
| `model_query.rs` | reading a project: `Project::new`, id allocation, the `clip` / `track` / `media` / `marker` / `nest` lookups, `clips_on`, `duration`, `validate` with its nesting walk, and `source_size` — the source's pixel size when the model knows it, `None` for text and for a media, nest or shape with no positive size. That last one was TWO private readers, `edit_props.rs`'s and `edit_background.rs`'s stricter one, collapsed here by road map 5's T0f, so a source kind added to `model.rs` is answered once. The three source-window measurements moved out to `source_window.rs` (road map 7 §10, phase A) |
| `frame_grid.rs` | One clip-time normalization concern (D7-3): placement start, `source_window.rs`'s bounded duration, action spans, present base motion/text timing and a graphic's `in` and `length` (through `recipe_graphic.rs`'s `graphic_resnapped`, §11 G-18). Called by canvas, both paste paths and unnest; source positions, action-end payloads and audio envelopes are untouched. |
| `source_window.rs` | THE source window — how much material a clip shows and how much lies either side of it, in the unit its name says (road map 7 §10, phase A). The three readers moved out of `model_query.rs` with their units in their names (`content_length_in_source`, `source_head_on_timeline`, `source_length_on_timeline`), `SourceBound` in place of the `Option` whose `None` meant two opposite things, `longest_duration_on_grid` (the bound, snapped DOWN — §11's #22), the two tail readers `slip` and `freeze_frame` clamp against, the five functions phase B added so that every writer of a media clip's window reads ONE bound (§11's D4-2 to D4-5) — `longest_duration_on_grid_of`, which takes the pieces with the clip's `start` among them, `latest_end_on_grid` and `earliest_start_on_grid`, the two timeline POSITIONS an edge is held to, `duration_resnapped`, what every re-snap of a media duration writes, and `duration_at_speed`, what `set_speed` writes — and the ONE mover — `in_advanced` / `source_advanced`, the `round(Δ × speed)` advance of a source in point that `trim_start`, `roll`, `split_clip`, `freeze_frame`, `slip` and `add_transition` each used to write out |
| `time_bounds.rs` | One structural-time envelope for read, edit completion and write (D7-1); it names the field and uses i128 for endpoints. |
| `transition_search.rs` | Bounded handle reduction and exact ripple forbidden intervals (D7-2); the final shifted project still passes the overlap rule. |
| `time.rs` | `Ticks`, `TIMESCALE`, `Fps`, frame snapping, timecode format/parse (non-drop `HH:MM:SS:FF` and `HH:MM:SS.mmm`) |
| `outcome.rs` | what an op ANSWERS (§5.5) — `Outcome`, with `Applied(Project)`, `Identity` and `Refused(String)`. An enum and not a side channel because a site that has not decided which of the three it gives does not compile, which is how the fourteen sites that used to throw a rule's sentence away were found (road map 7's D2). Its `Identity` doc is the ONE place that lists which refusals carry a sentence today, and the two families that stay identities on purpose |
| `edit.rs` | the op enum + serde, `apply(&self, op) -> Result<Outcome, String>`; **its module doc is the op table's SEMANTICS half**, where `op_table.rs` is its arguments, and it re-exports `OP_NAMES` at the path it has always had. `parse` answers an `Envelope` — the op AND the envelope's `scope` — which it takes out of the object in the pass that already reads `"op"`, because `Op` is internally tagged with `deny_unknown_fields` on every variant (an envelope key would be a typo to all fifty-seven) and serde does not support that attribute with `flatten`. `apply_op(&Op)` is unchanged and knows nothing about nests |
| `op_table.rs` | the op table as DATA (road map 7's D3): one row per op, one `Argument` per argument — name, `Kind`, required — and `OP_NAMES` as a projection of it rather than a list beside it. Its own module because the table is a PUBLISHED interface — every op tool in the catalog reads it rather than restating it (§7.9), and an `Argument` carries a `Bound` where the core REFUSES outside one, sourced from the constant that enforces it and never where the core merely clamps — and the `Op` enum and the fifty-seven-way dispatch are one implementation of it; a row carries no prose, no semantics and no default spelled twice, and `Kind` is closed with exactly one kind per answer serde can give, so every claim a row makes is one `core/tests/op_table.rs` can put to the decoder. Capped at 400 lines like any new module — `edit.rs`'s table exemption is not extended to it |
| `op_schema.rs` | the op table written as JSON SCHEMA — what `rc_op_schemas` publishes (road map 7's D3·2), one object per op whose properties are its arguments and whose `required` is the ones the decoder will not do without. A module of its own because a row changes when an OP does and this changes when the published DIALECT does, and the match over `Kind` is exhaustive so a kind cannot be added without saying what JSON it is. It publishes what an argument IS and never what it is FOR, an opaque object for a caller-authored patch (D1 is the one validator of what one may carry) and a `ZoomRegion`'s four declared members for the one caller-authored object the core does own, and no `additionalProperties` on an op, because the catalog merges `project` and `scope` in over it |
| `scope.rs` | editing INSIDE a nest — the envelope's `scope` key (road map 2, phase 9). Builds a VIEW project out of the nest, applies the op to it unchanged, and merges `tracks`, `clips`, `next_id`, `media` and `nests` back. Its own module because a scope is a change of CONTAINER rather than an op or a property of one, and because the whole of it is two pure functions and a refusal list, which belong nowhere near the semantics of any single edit. Three readings in it are measured rather than reasoned: the scoped nest's row stays in the view with its tracks and clips **emptied** (whole, it doubles every id in `validate`'s one uniqueness sweep; removed, it dangles every other nest's clip that shows it — the nest-inside-a-nest case the phase exists for); the nests write-back is **union first, orphans after**, because `unnest`'s `nest_is_shown` cannot see the parent's timeline clips from inside a view and would drop a nest a timeline clip still shows; and the caps and the depth are checked ONCE on the merged parent, which is why a scoped op has a wider `Err` arm than any other |
